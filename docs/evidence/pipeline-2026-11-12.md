## The run, step by step

Quoted from the live build (`C:/dossier-demo/run-output.txt` holds the full transcript).

**1. Ingest.** A Greenhouse board capture lands as corpus rows and records its coverage.

```text
$ dossier feeds fetch greenhouse --board acme --root … --limit 50 --json
{ "source": "greenhouse", "records": 3, "total": 3, "truncated": false, "complete": true }

$ dossier corpus build --root … --json
{ "rows": 3, "distinct_ids": 3, "duplicate_ids": 0, "sources": 1 }
```

The coverage snapshot `nz-job-search-coverage-2026-11-12.json` records
`source_statuses: {"greenhouse": "captured"}` and `current_source_counts: {"greenhouse": 3}`
(the producer added in `11a840a`).

**2. Filter.** Seven answers (five required) complete the profile; the match scores all
three rows and keeps the rejects listed with their reasons.

```text
$ dossier identity answer --from-json answers.json --root … --json
{ "answers": 7, "complete": true, "missing_required": [] }

$ dossier identity match --root … --json
"band_counts": { "strong": 0, "possible": 1, "unlikely": 2 }
```

The shortlist row, with visible arithmetic:

```text
Software Engineer · Acme · Hamilton — score 63, band "possible"
  reasons: title matches your target on: engineer, software
           1 must-have skills present: Python
           2 skills from your resume appear: Python, SQL
           location matches Hamilton
```

The two rejects stay in the report, named:

```text
Commission-only Sales Agent · Beta — "contains a deal-breaker: commission-only"
Senior Legal Counsel · Gamma     — "role reads senior and you are targeting graduate"
```

The grounded profile is then written to the workspace's identity document, and the fit
judgement is propagated onto the corpus (fit is a judgement over the measured bands —
here the demo's choice, strong→High, possible→Medium, unlikely→Low, disqualified→Skip —
never a re-score):

```text
$ dossier identity write --root … --json
{ "path": "workspace-IDENTITY.md", "fields": 8, "missing_required": [] }

$ dossier corpus propagate --ranking ranking.json --root … --json
{ "scored_before": 0, "scored_after": 3, "fits_after": { "Medium": 1, "Skip": 2 },
  "match_tiers": { "unique-url": 3 }, "unmatched": 0 }
```

**3. Tailor.** The user's own base document (`templates/base-resume.docx`), filled from a
spec; layout untouched, verified three ways.

```text
$ dossier tailor fields --template templates/base-resume.docx
Name / objective / Phone / Email

$ dossier tailor template --template … --spec fields.json --out variants/resume_acme-software-engineer.docx
filled 4 placeholders in 4 paragraphs

$ dossier verify template --template … --candidate … --spec fields.json
  [pass] no-leftover-placeholders — no placeholder survived
  [pass] values-present — all 4 supplied values appear in the document
  [pass] template-preserved — every untouched template paragraph survived
passed: True
```

**4. Letter.** Built from the tailored variant; it inherits the resume's own font and
section geometry rather than a default.

```text
$ dossier tailor cover-letter --base variants/resume_acme-software-engineer.docx --spec letter.json …
{ "font": "Cambria", "paragraphs": 8,
  "geometry": { "left": 90.0, "right": 90.0, "top": 72.0, "bottom": 72.0 } }
```

**5. Track.** The agent writes the row (`job-history.md` is user/agent-authored), then the
submission gate refuses until the user confirms:

```text
$ dossier track outcome 1 applied --root … --json
{ "written": false, "refused": "drafted-is-not-applied",
  "detail": "Refusing to mark a row applied: no confirmation that the user submitted it. …" }

$ dossier track outcome 1 applied --applied 2026-11-12 --confirmed --root … --json
{ "written": true, "row": 1, "status": "applied", "applied_date": "2026-11-12",
  "backup": "…\\.dossier\\trash" }

$ dossier track followup 1 --date 2026-11-12 --channel email --root … --json
{ "written": true, "line": "- 2026-11-12 · #1 email" }
```

(The test also refuses `--applied` without `--confirmed`; the gate holds either way.)

## Two bugs this run found, and their regression tests

1. **The agent had a second, drift-prone copy of the confirmed-date rule.**
   `agent/workspace._tracker_state` read applied dates only from `follow-ups.md`, so a row
   dated by `track outcome --applied --confirmed` (which writes the Notes column) was
   reported as undated: the first live run showed the blocker
   `Application rows without a confirmed 'Applied YYYY-MM-DD': [1]` while `track summary`
   already listed `{"1": "2026-11-12"}`. Fixed by reusing the engine's
   `tracker.applied_dates` / `ACTIONABLE` / parsed ordinals — the engine owns the rule.
   Regression: `tests/test_agent.py::test_workspace_reads_a_confirmed_date_from_the_tracker_notes`.

2. **`identity write`'s default filename was invisible to the rest of the system.** With no
   existing identity document it wrote `IDENTITY.md`, which matches neither the agent's
   `*-IDENTITY.md` blocker check nor the engine's document mining. The default is now
   `<workspace-name>-IDENTITY.md` (this run: `workspace-IDENTITY.md`). Regression:
   `tests/test_identity.py::test_write_names_a_new_document_so_the_workspace_can_find_it`;
   the e2e identity flow now asserts the discovery rule instead of a fixed filename.

Both are the repo's named pitfall — *two copies of one rule drift* — caught by running the
whole pipeline instead of the pieces in isolation, which is exactly what item D asked for.

## Naming notes

- The base is `base-resume.docx` because `tailor.is_base_document` requires "resume" or
  "cv" in the stem; the variant is `resume_acme-…` because `is_generated_document`
  recognises the `resume[_-]…` convention. The workspace now counts 1 base document and
  1 artefact, as the status above shows.
- The demo's identity answers are fictional demo data, not the owner's answers; the
  questionnaire's decision fields (`employment`, `right_to_work`, `target_roles`) remain
  the owner's to answer in a real workspace.
